# AMR kinematic calibration: cause of the yaw-rate mismatch

Date: 2026-10-22. No robot, Nav2, MPPI or localization parameter was changed; everything below is measurement and analysis.
Numbers in section 3 are regenerated by `identify_kinematics.py` (`kinematic_identification_numbers.md`).

## Conclusion

The wheel radius is correct (k_v = 1.00000). The yaw-rate error (k_w = 1.07812) is a **wheel-separation effect**: the simulated rotation behaves as if the wheels were **0.640 m** apart, not 0.690 m. The URDF geometry itself is correct and consistent. 0.640 m is exactly the spacing of the wheels' *inner edges* (0.690 - 0.050 wheel width), and a diagnostic with other wheel widths confirms that ws_eff tracks `0.69 - wheel_width`. This points to the simulator's contact model for the flat cylindrical wheels, not to a modelling mistake in the controller or URDF dimensions.

## 1. Geometry inspection

Sources: `src/amr_description/urdf/{amr.urdf.xacro, amr_properties.xacro}`, `src/amr_control/config/controllers.yaml`, the expanded URDF and the SDF Gazebo builds from it (`geometry/expanded.urdf`, `geometry/expanded.sdf`), the world file, and live ground-truth poses from Gazebo.

| item | nominal / modelled value | evidence |
|---|---|---|
| left / right wheel joint origin | y = +0.345 / -0.345 m, z = 0.100 m above `base_footprint` | expanded SDF `left_wheel_joint`, `right_wheel_joint` |
| wheel centre-to-centre separation | **0.690 m** (= base_width 0.60 + wheel_width 0.05 + 2 x clearance 0.02) | Gazebo ground-truth link poses: 0.69000 m |
| driven-wheel collision | cylinder, radius 0.100 m, length 0.050 m, axis along y, at joint origin; **no `<surface>` block** (engine default friction) | expanded SDF |
| controller `wheel_separation` / multiplier | 0.69 / 1.0 | `controllers.yaml`, read live from the running controller |
| controller `wheel_radius` / L-R multipliers | 0.10 / 1.0 / 1.0 | same |
| odometry mode | `open_loop: false`, `position_feedback: true` | same |
| casters | 4 spheres r = 0.04 m, fixed to the chassis, mu = mu2 = 0.01 | expanded SDF (the `<gazebo><mu1>` tags do translate to SDF friction) |
| ground plane | mu = mu2 = 1.0 | world file |
| physics | DART, 0.5 ms step | world file |
| wheel actuation | `gz_ros2_control` velocity interface, limit +-12 rad/s | URDF `ros2_control` block |

Nominal geometry vs effective rolling parameters: the nominal dimensions (r = 0.100 m, separation 0.690 m) are all realised exactly in the simulation. Effective values are what the contact model produces; they were measured, not inferred from the URDF. Nothing in the URDF was changed to match them.

Gazebo contact parameters that could matter: the wheels use default contact/friction (no per-wheel `<surface>`), and the wheel collision is a flat cylinder with a 0.05 m wide contact patch. The casters have almost no friction (0.01), so they do not resist rotation. I did not find any parameter that explains an inner-edge effect directly; the diagnostic below is the evidence.

## 3. Effective kinematics

From `kinematic_identification_numbers.md`:

| quantity | value |
|---|---|
| k_v | 1.00000 (4 of 4 tests) |
| k_w | 1.07812 (6 of 6 tests; baseline run `runs/20261022_102121_baseline`) |
| effective radius = 0.10 x k_v | **0.10000 m** |
| effective separation = 0.69 x k_v / k_w | **0.64000 m** |
| equivalent `wheel_separation_multiplier` | 0.92754 (not applied) |

Cross-checks from the recorded wheel angular velocities and Gazebo ground truth:
- r_eff = v_GT / mean(w_L, w_R) = 0.10000 m in all four straight tests.
- ws_eff = r_eff x (w_R - w_L) / w_GT = 0.64000 m in all six rotation tests.
- The identified model reproduces the ground-truth yaw rate to within 0.0001% for all six steps.

Does the evidence support radius, separation or both? **Separation only.** k_v = 1 rules out a radius error, and the separation estimate is the same at 0.4, 0.7 and 1.0 rad/s in both directions (no slip or speed dependence). The simple differential-drive model with ws = 0.640 m explains all 10 tests to better than 0.01%.

Mechanism diagnostic (not part of the robot; scratch copies of the model under the session scratchpad, joint spacing fixed at 0.690 m, only wheel width changed, run on one clean sim each):

| wheel width | measured ws_eff | 0.69 - width | residual |
|---|---|---|---|
| 0.10 m | 0.5900 m | 0.5900 m | +0.0000 |
| 0.05 m (actual robot) | 0.6400 m | 0.6400 m | +0.0000 |
| 0.02 m | 0.6723 m | 0.6700 m | +0.0023 |

The effective separation follows the inner-edge spacing of the wheels, which is consistent with the cylinder-on-plane contact being resolved at the inner rim (or with an equivalent bias). Contact points were not observed directly; this is an inference from three widths.

## 4. Unexplained or unverified points

1. **Contact mechanism is inferred, not observed.** The width scan fits inner-edge contact exactly at 0.05 m and 0.10 m, but at 0.02 m the effective separation is 0.0023 m (0.3%) larger than predicted. I do not know why; it may be contact softness or patch-width effects that matter more for thin wheels. It does not affect the actual 0.05 m robot.
2. **Fused pose yaw vs fused twist.** In the rotation baseline the EKF output twist matches ground truth (1.000), but the slope of its pose yaw is 0.982 of ground truth. The EKF fuses both the 7.8%-too-low wheel yaw rate and the correct IMU yaw rate, and its pose integrates a compromise. This is a consequence of the wheel-odometry error, not an independent fault, but I have not isolated the weighting.
3. **Process hygiene incident (resolved, data discarded).** Earlier shutdowns left orphaned `gz sim` servers sharing the Gazebo transport, so a first linear run and a first width-0.10 run recorded mixed data. Both were renamed `*_SUPERSEDED_multisim`, kept only for the record, and repeated on a single simulation (verified server count = 1 before each run). The baseline rotation run was recorded with a single simulation and is unaffected; its raw CSVs are untouched (only its derived report/plot were regenerated). All simulations are now closed.
4. **Single physics configuration.** Everything was measured with this world's DART settings, default wheel contact and 0.5 ms step. The 0.64 m value is a property of this simulation setup and should not be assumed to apply to the real vehicle.

## 5. Recommended correction (for your decision; nothing implemented)

Keep the URDF as is (its dimensions are real and correct) and correct the **controller's kinematic model** so that odometry and commands match the effective rolling behaviour:

- Set the diff_drive_controller effective separation to **0.640 m**, expressed as `wheel_separation_multiplier = 0.92754` (= 0.64 / 0.69), or equivalently `wheel_separation: 0.64` with multiplier 1.0. Do not change `wheel_radius` (k_v = 1.00000).

Justification: (a) the evidence isolates the error to separation alone and fits it to 5 significant digits across both directions and three speeds; (b) the nominal URDF geometry matches Gazebo's ground-truth link poses exactly, so editing it would misrepresent the robot; (c) the multiplier is the intended calibration knob and keeps the physical 0.69 m documented; (d) the correction brings raw wheel odometry, fused odometry and the IMU into agreement with ground truth, and makes commanded yaw rates (including the 1.2 rad/s controller limit and Nav2/MPPI angular commands) produce the same true body yaw rate.

Alternatives I do not recommend as the first step: changing the wheel width or collision shape in the URDF to remove the contact artefact (this alters the robot model and changes inertia and contact behaviour). If you prefer to remove the artefact at the source, the width scan suggests that the contact model, not the dimensions, is responsible, and that would be a separate simulation-fidelity task.

Suggested verification after you decide: rerun `run_rotation_test.py` (rotation) with the existing six steps and `analyze_rotation_test.py`; expect all source/ground-truth ratios of about 1.000, k_w about 1.000, and a straight-line rerun with unchanged k_v = 1.000. Note that parameters read live (`metadata.json`) will show the new separation, so `implied_ws` values will then be near the new controller value.

python3 calibration/yaw_rate_sysid/analyze_rotation_test.py RUN

    --diag RUN_W010:0.10 RUN_W002:0.02

Close the simulation after each session (kill the whole `ros2 launch` process group; orphaned `gz sim server` processes keep running otherwise).
