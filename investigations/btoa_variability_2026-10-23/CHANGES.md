# Protocol / driver changes during the pilot (chronological)

1. smoke01: client crashed (PyYAML parsed `1.0e9` as a string) and the bag recorder ignored SIGINT. Fixed (`timeout: 1000000000.0`; SIGTERM). Smoke runs are not counted.
2. p04_m0.92754 (13:15): Nav2 lifecycle bringup failed (`Failed to change state for node: planner_server`); the driver's readiness probe had no timeout and hung ~28 min. Aborted by the operator, labeled `INFRA_NAV2_BRINGUP_FAILED`, kept, not counted. Driver hardened: timeout on every ROS CLI probe, 150 s readiness deadline, immediate abort on "Failed to bring up all requested nodes".
3. p04_m0.92754_retry1 re-run of that slot (driver v1 otherwise).
4. From p05 on: **driver v2**: the all-node parameter dump runs 8-way parallel (was sequential, ~125 s per run). The dump happens while the robot is idle before the goal, so only the idle time between "ready" and "goal sent" changes (≈ 2.5 min -> ≈ 30 s). Each run's `driver_version.txt` records which driver produced it. p05 is the 1.0 arm and p06 the 0.92754 arm, so the change is spread across both arms. Reason: operator time constraint.
5. p05_m1.0 (13:50): Nav2 bringup failed (`Failed to activate global_costmap because transform from base_footprint to map did not become available before timeout`; EKF `Failed to meet update rate`): a startup failure under heavy machine load (load average > 10 on 16 cores, browser + desktop + RViz + Gazebo GUI). Labeled `INFRA_NAV2_BRINGUP_FAILED`, kept, not counted; driver retried as `p05_m1.0_retry1` (13:53). The first p04 failure had the identical cause.
6. ~13:56 (operator): the browser and other desktop applications were closed, so machine load is LOWER for the runs that start after this time than for p01-p04 and the first part of p05_retry1's setup. This is an uncontrolled change in background load; `load_snapshot_start.txt` and `sysmon.csv` of every run record the load actually present. The decision to keep the Gazebo GUI and RViz running was the operator's (option "continue as is").
7. 14:02 PILOT RESULT: 5 valid runs (p01,p03 = 1.0; p02,p04_retry1,p06 = 0.92754), all SUCCESS; 3 infrastructure failures (p04 first attempt, p05, p05_retry1) not counted; p05's slot has no valid run, so the 1.0 arm has only 2 valid pilot runs. No failure was captured, so the pilot cannot distinguish the hypotheses. Per the protocol ("extend only if the available results cannot distinguish the leading hypotheses") an EXTENSION of 4 pairs (e01..e08, interleaved, driver v2, lower desktop load than p01-p04) was started. The pilot is NOT re-analysed with different thresholds; the classification criteria are unchanged.
8. 14:11 e03_m1.0 (and p04's first attempt, p05) hit a lost RMW service response at startup: `[amcl.rclcpp]: failed to send response to /amcl/change_state (timeout)` (earlier: the same message from smoother_server). AMCL then never activated, no `map` frame existed (RViz: "Frame [map] does not exist"), the planner kept waiting and Nav2 aborted bringup after ~73 s. Driver v3 (applies from the next run started after this edit) aborts immediately on that message and retries once. This is a startup/infrastructure flake, not part of the experiment; such runs are labeled INFRA_* and not counted.
9. 14:17 e01 (spin) and e03_retry1 were extracted/analysed with 'nice' while e04 was running (light, short CPU use); recorded here because it is a small concurrent load.
10. 14:21 Operator stopped the extension after e05 (time constraint). e06, e07, e08 were NOT run. Final sample: pilot p01-p06 + e01-e05 (valid runs counted per classification). Stopping was a time decision, not an outcome-based one.
11. 14:24 e05_m1.0: one 'ros2 param dump /bt_navigator_navigate_through_poses_rclcpp_node' hung 4+ min (CLI ignores SIGTERM while blocked; log shows dropped service responses, e.g. 'bt_navigator ... failed to send response to /bt_navigator/get_parameters'). Operator-visible symptom: goal not sent. The hung dump process was killed with SIGKILL so the run could proceed; that node's parameter file is missing/empty. Script now uses 'timeout -k 2' (SIGKILL after 2 s) for the dump. e05 is flagged: the middleware was dropping service responses during this run's setup.
12. 2026-10-24 Addendum analysis (offline, no new runs): upstream nav2_mppi_controller 1.3.12 source read (archived under analysis/addendum/mppi_1.3.12_source_used/); corrections to the main report listed in Addendum section 6 (cusp artefact; MPPI noise is fixed per goal, not random per cycle; 'no source available' superseded). Main report left unchanged.
